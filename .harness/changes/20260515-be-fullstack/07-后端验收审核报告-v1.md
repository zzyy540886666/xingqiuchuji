## 1. 验收结论

**验收结论：不通过。**

后端代码已经覆盖了认证、商品、订单、支付、会员、钱包、分销、社区、报修运维后台等大量模块入口，但当前不能通过真实生产验收。阻断原因集中在：

- 微信支付 JSAPI 与支付回调仍存在空配置、占位取值、签名字符串错误，无法完成真实支付闭环。
- 微信商家转账/提现签名与 openid/appid 获取仍是占位实现，无法完成真实出款。
- `.harness` CI 门禁要求 `status=SUCCESS`、`tests>0`、`passed=total`；本轮 `mvn.cmd test` 可结束为 `BUILD SUCCESS`，但 `src/test` 与 `target/surefire-reports` 均无测试文件/报告，门禁判定为 `tests=0`，不通过。
- 部分 API 契约未实现或实现偏离，包括 `/users/me`、`/analytics/events`、`Idempotency-Key` 请求头语义。

## 3. 审核问题清单

### P0-1 微信支付 JSAPI 与回调链路仍为占位实现，生产不可用

- 问题：`backend/src/main/java/com/xingqiu/server/payment/adapter/WeChatPayClient.java:63`、`:67`、`:75` 构造微信支付请求依赖 `getAppId()`、`getNotifyUrl()`、`getPayerOpenid()`，但这些方法在 `:179`、`:180`、`:181` 全部返回空字符串；`:182` 的商户证书序列号也返回空字符串。`:162` 的小程序调起支付签名串硬编码为 `"wx-app-id\n"`，不是实际 appid。`:117`、`:118` 试图从 `extractHeader()` 读取微信回调头，但 `:183` 返回空字符串。`backend/src/main/java/com/xingqiu/server/payment/controller/WeChatNotifyController.java:21` 的回调入口只读取 `Wechatpay-Signature`，没有接收 `Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Serial`，无法完成微信支付回调验签。该实现不满足 `docs/backend/BE-04-支付与微信回调.md:5`、`:6` 的预支付、验签、解密、幂等要求，也不满足 `docs/architecture/03-安全合规与观测性.md:11` 的支付回调安全要求。
- 建议：接入真实微信支付配置与证书：appid、mchid、商户证书序列号、商户私钥、APIv3 Key、notifyUrl、用户 openid；优先使用微信支付官方 SDK 或等价的标准签名/验签实现。回调 controller 必须接收并传递 `Wechatpay-Timestamp`、`Wechatpay-Nonce`、`Wechatpay-Serial`、`Wechatpay-Signature` 和 body，完成验签、解密、`out_trade_no/transaction_id` 幂等更新，并补充微信沙箱或测试商户联调证据。
- 优先级：P0

### P0-2 微信商家转账/提现链路仍为占位实现，生产不可用

- 问题：`backend/src/main/java/com/xingqiu/server/wallet/adapter/WeChatTransferClient.java:44`、`:55` 依赖 appid 与用户 openid，但 `:97`、`:98` 返回空字符串。`:86` 创建 `SHA256withRSA` 签名器后，`:87` 注释标明私钥注入仍是 placeholder，`:88` 返回空字节数组的 Base64。该实现即使业务层扣减余额，也不能真实调用企业付款/商家转账，违反 `docs/backend/BE-07-钱包光年币与提现.md:6` 的“调用企业付款到零钱、失败可重试”要求，以及 `docs/architecture/03-安全合规与观测性.md:13` 的提现风控与企业付款要求。
- 建议：完成微信商家转账真实适配：注入商户私钥、证书序列号、appid、mchid、用户 openid 映射；实现标准 Authorization 签名；对微信响应码、转账批次号、失败重试、人工处理状态做持久化。提现验收必须包含真实沙箱/测试商户联调或可复现的集成测试。
- 优先级：P0

### P0-3 `.harness` 测试门禁不通过，当前无后端自动化测试

- 问题：`.harness/README.md:29`、`:30` 要求 CI 状态 `status=SUCCESS` 且 `tests>0`；`.harness/skills/unit-test-write/SKILL.md:38`、`:39`、`:54` 要求 `status=SUCCESS`、`tests>0`、`passed=total`。本轮 `mvn.cmd test` 可以结束为 `BUILD SUCCESS`，但 `backend/src/test` 下没有测试文件，`backend/target/surefire-reports` 也没有测试报告，实际门禁为 `tests=0`。按 `.harness/rules/02-开发流程规范-阶段与门禁.md:26`，`tests=0` 必须回退到单测编写。
- 建议：补齐后端自动化测试并纳入 Maven/Surefire 可读报告。最低应覆盖认证 token 校验、订单试算/创建/状态机、支付回调验签与幂等、钱包流水与提现、资源归属鉴权、报修工单状态流转、异常响应 envelope。CI 报告需产出 `status=SUCCESS`、`tests>0`、`passed=total`。
- 优先级：P0

### P1-1 幂等实现与 API 契约不一致，存在重复提交和误拦截风险

- 问题：`docs/api/00-接口通则.md:68` 要求支付、创建订单、提现使用 `Idempotency-Key: <UUID>` 请求头，并由服务端 Redis/DB 去重 24h。当前 `backend/src/main/java/com/xingqiu/server/common/interceptor/IdempotencyInterceptor.java:20` 读取请求头，但 `backend/src/main/java/com/xingqiu/server/order/dto/CreateOrderRequest.java:22` 又把 `idempotencyKey` 放在 body，`backend/src/main/java/com/xingqiu/server/order/controller/OrderController.java:35` 未通过 `@RequestHeader` 将请求头传入业务层，`backend/src/main/java/com/xingqiu/server/order/service/OrderService.java:53`、`:84` 只保存 body 中的幂等键。另一方面，`backend/src/main/java/com/xingqiu/server/common/config/WebMvcConfig.java:20` 将拦截器挂到 `/api/v1/orders/**`，会覆盖订单预览、支付等非同一语义请求；`IdempotencyInterceptor.java:39` 在业务事务前先写 Redis，失败后也会占用 key，`:42` 对重复请求直接返回冲突而不是返回原结果或处理中状态。
- 建议：把幂等控制收敛到具体命令服务层，以 `userId + endpoint/action + Idempotency-Key` 建唯一约束；创建订单、发起支付、提现分别明确幂等语义。首次请求应持久化请求指纹、处理状态与响应摘要；重复请求在请求指纹一致时返回原结果或“处理中”，指纹不一致时返回契约化错误。拦截路径不能粗暴覆盖 `/orders/**`。
- 优先级：P1

### P1-2 缺失 `/api/v1/users/me`，认证与用户契约未闭环

- 问题：`docs/api/API-01-认证与用户-运营配置.md:36` 要求 `GET /users/me` 返回当前用户资料。代码扫描只发现 `backend/src/main/java/com/xingqiu/server/member/controller/MemberController.java:22` 的 `/users/me/membership` 和后台 `/api/v1/admin/users`，没有面向小程序的 `GET /api/v1/users/me`。前端真实登录后无法按 API-01 获取当前用户档案、角色、头像昵称等基础信息。
- 建议：新增用户 controller/service，提供 `GET /api/v1/users/me`，从当前 Bearer token 解析 userId，返回用户基础资料、角色、会员摘要等 API-01 约定字段；补充鉴权、空用户、禁用用户测试。
- 优先级：P1

### P1-3 缺失 `/api/v1/analytics/events`，分销与埋点契约未实现

- 问题：`docs/api/API-06-分销与埋点.md:18` 要求 `POST /analytics/events`。代码扫描 `backend/src/main/java` 未发现 analytics/events 相关 controller/service，仅有文档和业务事件表实体。该缺口会导致前端埋点、分销归因、运营分析无法按 API-06 落地。
- 建议：新增 Analytics/Event 模块，支持批量事件上报、字段白名单、用户/设备/session 关联、去重、限流与异步落库；敏感字段脱敏，并补齐 API 与测试。
- 优先级：P1

### P1-4 报修与社区等写接口缺少请求体验证，存在脏数据与越权入口风险

- 问题：多个外部写接口未使用 `@Valid` 或直接接收 `Map`：`backend/src/main/java/com/xingqiu/server/community/controller/CommunityController.java:36`、`backend/src/main/java/com/xingqiu/server/repair/controller/WorkOrderController.java:35`、`:68`、`:87`、`:97`、`:107`，`DeviceController.java:37`、`:45`，`InspectionController.java:41`、`:48`、`:56`、`:87`，`KnowledgeController.java:38`、`:48`，`FeedbackController.java:29`、`:48`，`QrCodeController.java:22`。这些接口涉及工单、设备、巡检、知识库、反馈等生产数据，缺少 Bean Validation 会让非法状态、空字段、越界值进入业务层。
- 建议：所有外部 `@RequestBody` DTO 补齐 `@Valid`，DTO 字段补齐 `@NotNull`、`@NotBlank`、`@Min`、`@Max`、`@Size`、枚举校验等约束；避免裸 `Map` 承载生产写请求。对资源归属、角色权限、状态迁移前置条件在 service 层二次校验。
- 优先级：P1

### P1-5 OpenAPI 未体现“代码生成的唯一真源”，契约无法机验

- 问题：`docs/architecture/02-技术选型与部署拓扑.md:45` 要求路径、Schema、枚举以 `docs/api/openapi/openapi.yaml`（由代码生成）为唯一真源；`docs/api/README.md:7` 也要求 openapi 由 springdoc-openapi 生成后提交。但当前 `docs/api/openapi/openapi.yaml:10` 仍使用 `https://api.example.com/api/v1`，文件规模与实际 controller 数量明显不匹配，不能作为当前后端真实契约快照。API 文档、代码与前端调用无法通过 OpenAPI 做一致性校验。
- 建议：接入 springdoc-openapi 或等价生成流程，从当前 Spring Boot 代码导出 `/v3/api-docs.yaml` 覆盖 `docs/api/openapi/openapi.yaml`；CI 中加入 openapi diff 或契约检查，确保新增/变更接口必须同步文档。
- 优先级：P1

### P1-6 管理端 SKU Controller 承载事务和 Mapper 调用，违反分层约束

- 问题：`backend/src/main/java/com/xingqiu/server/admin/controller/AdminSkuController.java:23`、`:24`、`:25` 直接注入 `SkuMapper`、`SkuMediaMapper`、`SkuPriceMapper`，`:35`、`:44`、`:55`、`:69`、`:83` 在 controller 方法上使用 `@Transactional` 并直接执行业务写入。该实现把参数入口、事务边界、数据访问和业务编排混在 controller，违反 `.harness` 与后端分层中 controller 只做参数/响应适配、service 承担业务与事务的要求，也降低了权限、审计、测试的可控性。
- 建议：新增 `AdminSkuService`，由 service 承担事务、SKU/价格/媒体编排、审计记录和异常语义；controller 仅做鉴权上下文、参数校验与 response 包装。补齐 service 单测和 controller 契约测试。
- 优先级：P1

### P2-1 traceId 观测性仍不完整，安全层异常可能脱离统一响应

- 问题：`docs/architecture/03-安全合规与观测性.md:27` 要求 traceId 写入日志与错误响应。当前 `backend/src/main/java/com/xingqiu/server/common/filter/TraceIdFilter.java:26` 生成 traceId，`:30` 清理 traceId，但未写入响应头；`backend/src/main/java/com/xingqiu/server/common/config/SecurityConfig.java:60` 使用 `anyRequest().authenticated()`，未看到定制 `AuthenticationEntryPoint`/`AccessDeniedHandler` 将 401/403 包装为统一 `ApiResponse`。业务异常可带 traceId，但鉴权失败等安全层异常可能与 API 通则 envelope 不一致。
- 建议：在 `TraceIdFilter` 中设置 `X-Trace-Id` 响应头；为 Spring Security 配置统一的 `AuthenticationEntryPoint` 和 `AccessDeniedHandler`，保证 401/403 也返回 `{success,data,error,traceId}`。
- 优先级：P2

## 4. 七维度验收判定

| 维度 | 判定 | 说明 |
| --- | --- | --- |
| 需求一致性 | 不通过 | BE-04 支付、BE-07 提现存在 P0 占位实现；API-01、API-06 缺失接口 |
| 架构一致性 | 不通过 | 管理端 controller 直接持有事务和 Mapper；OpenAPI 未按代码生成作为真源 |
| 契约一致性 | 不通过 | `/users/me`、`/analytics/events` 缺失；`Idempotency-Key` header 语义偏离 |
| 安全性 | 不通过 | 支付回调验签链路不可用；提现签名占位；写接口校验不足 |
| 数据一致性 | 不通过 | 幂等在事务前抢占 key，重复请求不能安全重放；支付/提现状态无法真实闭环 |
| 可观测性 | 有风险 | traceId 已有基础能力，但安全层错误与响应头不完整 |
| 可测试性 | 不通过 | `tests=0`，无后端自动化测试报告，违反 `.harness` 门禁 |

## 5. 建议整改顺序

1. 立即修复 P0：支付 JSAPI/回调、微信商家转账/提现、后端自动化测试门禁。
2. 修复幂等模型：以请求头为契约真源，业务层持久化请求指纹、状态与响应摘要。
3. 补齐 API-01 `/users/me` 与 API-06 `/analytics/events`，并同步 OpenAPI。
4. 补齐外部写接口 Bean Validation、资源归属校验、状态迁移前置校验。
5. 调整管理端 SKU 分层，把事务和 Mapper 访问移入 service。
6. 重新生成 `docs/api/openapi/openapi.yaml`，用 CI 校验代码与契约一致性。
7. 重新运行 `mvn test` 并产出 `tests>0`、`passed=total` 的可机验报告，再生成验收报告 v2。

## 6. 最终判定

本轮后端验收 **不通过**。

回退目标：回到编码实现/编码评审阶段，优先修复 P0 问题；P0 未清零且 `.harness` 测试门禁未满足前，不建议进入生产部署、真实支付/提现上线或前后端联调验收结论归档。
