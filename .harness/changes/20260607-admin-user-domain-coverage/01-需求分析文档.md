# 用户域后台可见/可管需求分析

## 1. 需求来源

- 来源：用户于 2026-06-07 提出补充要求：
  - “我的订单、钱包、会员中心、我的资产、托管收益、分销中心、我的报修、消息”等用户数据，都要能够在后台管理网站查看。
  - 凡是相关需要管理、编辑的数据，也要能够在后台管理网站进行受控编辑。

## 2. 目标与范围

### 2.1 目标

建立后台管理网站对用户域数据的完整管理闭环：

1. 运营/客服/财务/运维可按权限查看用户侧核心业务数据。
2. 需要人工介入的业务数据，提供“受控操作”而非绕过业务规则的直接改库。
3. 后台页面、后台接口、OpenAPI 契约和小程序用户端语义保持一致。

### 2.2 本次纳入范围

- 我的订单
- 钱包
- 会员中心
- 我的资产
- 托管收益
- 分销中心
- 我的报修
- 消息

### 2.3 范围边界

- “可编辑”默认理解为**受控管理动作**，不是允许后台直接篡改金额、支付结果、钱包余额、佣金结果或订单状态机。
- 涉及金额、支付、提现、佣金、收益等数据，必须遵守“整数分 + 审计 + 幂等 + 权限控制”。
- 任何新增后台能力，最终都要补齐到 `docs/api/openapi/openapi.yaml`。

## 3. 现状梳理结论

## 3.1 总体判断

当前仓库已经具备部分后台用户域能力，但覆盖不完整，呈现为“部分已有列表页/骨架页，部分已有后端接口，部分仍明显缺口”。

现有后台导航已包含订单、用户、资金、报修等入口，但尚未形成对上述 8 个用户域的完整可见/可管闭环。

## 3.2 分域现状矩阵

| 领域 | 后台现状 | 现状判断 | 主要缺口 |
| --- | --- | --- | --- |
| 我的订单 | 已有订单列表、订单详情页面入口 | 部分具备 | 缺少完整详情接口、状态流水、支付/合同/异常追踪、受控处置动作 |
| 钱包 | 已有钱包流水、提现审核 | 部分具备 | 缺少按用户的钱包详情、余额勾稽、资金轨迹、对账异常工作台 |
| 会员中心 | 用户详情可看到部分会员字段 | 能看摘要，不能完整管理 | 缺少独立会员中心、会员权益/星球卡/等级运营能力 |
| 我的资产 | 用户详情中有托管资产摘要 | 仅摘要 | 缺少资产列表、资产详情、托管状态、收益联查 |
| 托管收益 | 领域层和用户端已有收益模型 | 后台基本缺失 | 缺少收益台账、按资产/用户筛选、结算/核对视图 |
| 分销中心 | 已有概览、佣金列表、结算批次 | 部分具备 | 缺少更完整的结算处理、冻结/冲正、批次详情与联查 |
| 我的报修 | 已有设备、工单、巡检列表与部分流转动作 | 相对完整 | 缺少工单详情、日志、反馈联查、巡检计划编辑闭环 |
| 消息 | 用户端消息接口已存在 | 后台基本缺失 | 缺少消息中心、模板、发送、投放结果追踪 |

## 5. 需求落地解释（建议口径）

为了防止“后台可编辑”被误解为可直接改账/改状态，本次建议按以下口径设计：

### 5.1 可查看（后台必须具备）

1. **列表能力**：支持分页、筛选、关键字搜索。
2. **详情能力**：查看用户侧详情、状态、时间线、关联对象。
3. **联查能力**：同一用户可串联查看订单、钱包、会员、资产、收益、分销、报修、消息。
4. **审计能力**：高风险对象可查看 traceId、事件流、操作者和异常原因。

### 5.2 可管理/可编辑（后台按权限提供）

1. **订单域**：异常标记、备注、人工跟进、合同查看、支付结果追踪；不直接改金额。
2. **钱包域**：提现审核、重试、风控备注、对账异常处理单；不直接改余额。
3. **会员域**：会员展示配置、会员权益开通/冻结等受控动作；不直接绕过支付规则。
4. **资产/托管收益域**：托管状态查看、收益核对、异常登记；不直接手工伪造收益结果。
5. **分销域**：佣金批次查看、结算状态跟踪、异常工单；不直接手改分佣金额。
6. **报修域**：派单、改派、加急、关闭、巡检计划维护。
7. **消息域**：消息查询、模板管理、定向发送/批量发送、发送结果追踪。

## 6. 推荐的后台信息架构与能力目标矩阵

### 6.1 后台菜单与模块落位

为满足“一次性覆盖 8 个用户域”的要求，后台信息架构至少应补齐到以下落位：

- **订单与履约**
  - 订单列表
  - 订单详情
- **用户与权益**
  - 用户列表/用户详情
  - 会员中心
  - 资产管理
  - 托管收益
- **资金与分销**
  - 钱包流水
  - 提现审核
  - 分销中心
- **运维管理**
  - 报修工单
  - 巡检管理
- **消息中心**
  - 消息记录
  - 模板管理
  - 发送任务/发送结果

### 6.2 八个用户域的最小交付单元

| 领域 | 后台模块落位 | 最小查看交付 | 受控管理动作 | 明确禁止后台直改 |
| --- | --- | --- | --- | --- |
| 我的订单 | 订单与履约 / 订单列表、订单详情 | 列表、详情、状态流水、支付记录、合同、异常信息、traceId | 备注、异常标记、人工跟进、合同查看、协作处置入口 | 金额、支付结果、订单状态机结果 |
| 钱包 | 资金与分销 / 钱包流水、提现审核 | 用户钱包详情、余额、流水、提现记录、对账差异 | 提现审核/拒绝/重试、风控备注、异常处理单 | 钱包余额、历史流水金额 |
| 会员中心 | 用户与权益 / 会员中心 | 会员等级、开通记录、星球卡摘要、权益摘要 | 权益配置、展示配置、受控冻结/开关 | 绕过支付直接赠送形成未审计权益 |
| 我的资产 | 用户与权益 / 资产管理 | 资产列表、资产详情、托管状态、租用情况、关联用户 | 托管运营配置、异常登记、协作处理 | 直接伪造资产归属或租用结果 |
| 托管收益 | 用户与权益 / 托管收益 | 收益摘要、收益流水、按资产/用户联查、结算状态 | 核对、结算确认入口、异常修复流程 | 直接手工改收益金额或已结算结果 |
| 分销中心 | 资金与分销 / 分销中心 | 分销关系、团队、佣金记录、批次详情、状态时间线 | 结算跟踪、异常工单、冲正规则入口 | 直接手改分佣金额或结算结果 |
| 我的报修 | 运维管理 / 报修工单、巡检管理 | 工单列表、详情、日志、巡检任务、反馈 | 派单、改派、加急、关闭、巡检计划维护 | 绕过工单状态机直接伪造完成结果 |
| 消息 | 消息中心 / 消息记录、模板管理、发送任务 | 用户消息、系统通知、发送记录、投放结果 | 模板管理、定向/批量发送、重发、上下线 | 绕过审计静默发送或删除已发送结果 |

### 6.3 跨域联查能力

后台除各域独立页面外，还必须提供“用户中心联查视图”，至少支持从单个用户串联查看：

- 订单
- 钱包
- 会员
- 资产
- 托管收益
- 分销关系与佣金
- 报修工单
- 消息记录

该联查视图是客服、财务、运营定位问题的最小工作台，不可只保留分散列表页。

## 7. 本次需求的实现缺口

### 7.1 P0 缺口

1. 缺少完整后台信息架构来承载“会员中心 / 资产 / 托管收益 / 消息中心”。
2. 已有订单、用户、钱包、分销、报修能力仍以列表和摘要为主，详情与联查不足。
3. 后台接口与 `openapi.yaml` 未形成完整 admin 契约闭环。
4. 现有后台实现存在 Controller 直连 Mapper 的越层模式，若不在需求阶段立为门禁，后续会延续错误分层。
5. 高风险动作的 RBAC、原因必填、审计记录、幂等与状态机约束尚未作为显式交付边界固化。

### 7.2 P1 缺口

1. 审计字段与操作留痕在多个后台域仍不统一。
2. 多数域未形成标准化导出、异常跟进、备注协作机制。
3. 缺少可复用的后台“详情页 + 时间线 + 联查侧栏”设计模式。

## 8. 强制设计与实现门禁

### 8.1 契约门禁

1. admin 用户域接口必须先补齐到 `docs/api/openapi/openapi.yaml`，再进入前后端联调。
2. OpenAPI 必须覆盖：路径、请求参数、详情 DTO、列表 DTO、状态枚举、错误码、鉴权要求、受控动作入参。
3. 后台前端接口封装与后端实现均以 OpenAPI 为唯一契约真源。

### 8.2 分层门禁

1. 后台 Controller 只负责参数校验、鉴权入口、错误映射。
2. 查询编排与高风险状态动作必须走 Service / Domain，不允许 Controller 直接调用 Mapper 拼业务结果。
3. 资金、收益、分销、工单、会员权益等领域规则不得下沉到前端或 Controller 临时拼接。

### 8.3 安全与权限门禁

1. 高风险动作必须有 RBAC 权限点，粒度至少到“资源 + 动作”。
2. 需要时预留数据范围控制（按区域、门店、业务域、角色）。
3. 冻结、审核、发送、结算类动作必须要求原因说明，并写入审计日志。
4. 后台只允许受控流程操作，不允许直接改账、直接改支付结果、直接改分佣结论、直接改收益结果。

### 8.4 数据一致性门禁

1. 金额统一为整数分。
2. 订单、支付、提现、分佣、收益类关键动作必须幂等。
3. 每个域在实施前都要定义合法状态迁移和禁止状态跳跃规则。
4. 后台详情 DTO 必须与用户端语义一致，避免前端期望字段与后端返回不一致。

### 8.5 可观测性门禁

1. 用户域详情页应能查看必要事件流水、异常原因和 traceId。
2. 高风险操作必须记录操作者、对象、前后值、原因、时间、traceId。
3. 异常处理与受控动作要支持后续审计和问题追溯。

### 8.6 可测试性门禁

1. 后台用户域必须补齐最小测试矩阵，覆盖权限、契约、状态迁移、幂等和异常路径。
2. 联查视图至少验证关键数据拼装与空态/错误态。
3. 高风险动作必须有后端测试，不允许只依赖前端交互校验。

## 9. 最小验证矩阵（供阶段3/4拆分使用）

| 验证类别 | 最小要求 |
| --- | --- |
| 契约验证 | admin 用户域接口已进入 OpenAPI，并与前端调用一致 |
| 权限验证 | 查询与高风险动作具备 RBAC 校验，越权返回一致错误码 |
| 详情验证 | 8 个域详情页字段与后端 DTO 一致，空态/错误态完整 |
| 状态机验证 | 提现、工单、会员冻结、消息发送、结算跟踪等动作符合合法迁移 |
| 幂等验证 | 提现重试、消息重发、结算确认、异常修复等重复提交不产生重复结果 |
| 审计验证 | 高风险动作记录操作者、原因、traceId、前后值 |
| 联查验证 | 从单用户视角能串联查到 8 个域核心数据 |

## 10. 已确认决议项

| 决议项 | 用户确认结果 | 本次采用口径 |
| --- | --- | --- |
| 编辑边界 | 仅受控流程 | 订单/钱包/分销/托管收益等资金与状态数据，不允许后台直接改业务结果，只允许审核、重试、备注、异常处理、冻结/解冻等受控动作 |
| 消息范围 | 模板 + 发送 | 后台纳入消息查询、模板管理、定向/批量发送、发送结果追踪 |
| 会员范围 | 含权益配置 | 会员中心不仅查看用户会员数据，还纳入星球卡/权益配置与受控开关 |
| 建设顺序 | 一次性全做 | 本轮目标不是分批只补局部域，而是统一覆盖 8 个用户域的查看与管理闭环 |

## 11. 当前阶段结论

该需求成立，且与现有 `docs/admin/01-后台管理网站需求文档.md` 的“用户与权益 / 资金与分销 / 订单与履约 / 运维管理 / 内容与消息”方向一致，但本次用户要求已进一步明确为：

1. 8 个用户域一次性纳入后台；
2. 资金/状态类数据仅允许受控流程管理，不允许后台直改结果；
3. 消息域纳入模板、发送与结果追踪；
4. 会员域纳入权益配置；
5. 需求阶段即固化 OpenAPI、分层、RBAC/审计、幂等、状态机和测试门禁。

在上述要求写清后，可重新进入阶段2需求评审；评审通过后再进入阶段3任务拆分。
