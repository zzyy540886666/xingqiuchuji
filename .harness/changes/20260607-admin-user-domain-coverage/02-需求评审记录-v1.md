## 3. 7 维度评审意见

### 3.1 需求一致性

- **问题**：当前需求已明确“一次性覆盖 8 个用户域的后台可见/可管闭环”，但现状分析虽然指出缺口，仍未把“后台菜单落位、每域详情页、联查能力、受控动作边界”固化为明确交付对象，后续拆分时容易退化为只补若干列表页。
- **建议**：在需求基线中补充每个域的最小交付单元：列表、详情、联查、受控动作、禁止直改边界，并明确会员中心、资产/托管收益、消息中心必须作为独立后台能力落位。
- **优先级**：P0
- **证据**：`01-需求分析文档.md`、`docs/admin/01-后台管理网站需求文档.md`、`admin-web/src/router/index.ts`

### 3.2 架构一致性

- **问题**：现有后台实现大量由 Controller 直接依赖 Mapper 进行查询或状态写入，破坏五层架构边界。如果需求文档不把“后台用户域能力必须经 Service/Domain 受控编排”写为硬约束，后续实现会继续沿用当前越层模式。
- **建议**：在需求基线与任务拆分前置约束中明确：后台查询和高风险管理动作必须通过 Service/Domain 编排；Controller 仅做参数校验、鉴权入口和错误映射。
- **优先级**：P0
- **证据**：`.harness/rules/01-工程结构-模块职责-五层架构.md`、`AdminUserController.java`、`AdminOrderController.java`、`AdminFinanceController.java`、`AdminDistributionController.java`、`AdminRepairController.java`

### 3.3 契约一致性

- **问题**：当前用户域后台接口已经在代码中存在，但 `docs/api/openapi/openapi.yaml` 尚未形成对应的完整 admin 契约闭环；若不先固化契约，阶段3/4 会继续出现“前端先写页面、后端临时补字段”的漂移。
- **建议**：把“先补齐 admin 用户域 OpenAPI，再实施前后端”的顺序提升为本需求 P0 门禁；至少明确后台路径、DTO、枚举、错误码、鉴权要求和详情字段。
- **优先级**：P0
- **证据**：`docs/api/openapi/openapi.yaml`、`AdminUserController.java`、`AdminOrderController.java`、`AdminFinanceController.java`、`AdminDistributionController.java`、`AdminRepairController.java`

### 3.4 安全性

- **问题**：当前后台更多是粗粒度 `ADMIN` 访问控制，尚未体现“资源 + 动作 + 数据范围”的 RBAC，也未把高风险动作的原因必填、二次确认、审计落库作为后端强约束。需求文档若不把这些列为必做项，后续极易只做前端弹窗确认。
- **建议**：在需求基线中补充：账号冻结、提现审核、工单流转、消息发送、权益开关、结算相关动作必须具备后端权限点、原因必填、数据范围校验和审计记录。
- **优先级**：P0
- **证据**：`docs/admin/01-后台管理网站需求文档.md`、`backend/src/main/java/com/xingqiu/server/common/config/SecurityConfig.java`、`AdminUserController.java`

### 3.5 数据一致性

- **问题**：多个现有后台动作本质仍是直接改状态，缺少状态机、幂等与勾稽保护；同时前端详情页期望的数据字段与后端现有返回并不完整匹配。若需求阶段不明确“详情 DTO / 状态迁移 / 幂等规则”，后续实现会继续产生语义断裂。
- **建议**：在需求基线中为订单、钱包、会员、资产、托管收益、分销、报修分别明确：详情字段、时间线字段、合法状态迁移、幂等约束、禁止后台直改的对象。
- **优先级**：P0
- **证据**：`.harness/rules/03-工程硬性规范.md`、`AdminFinanceController.java`、`AdminRepairController.java`、`AdminOrderController.java`、`admin-web/src/modules/users/UserDetail.vue`

### 3.6 可观测性

- **问题**：需求已要求后台可查看 traceId、事件流、操作者和异常原因，但当前分析未把“后台关键操作的 trace / 审计 / 事件流水字段”单列为强制交付，容易在实现时被忽略。
- **建议**：在需求基线中补充可观测性要求：用户域详情页应能查看必要事件流水；高风险操作必须记录 traceId、操作者、对象、前后值、原因、时间。
- **优先级**：P1
- **证据**：`docs/admin/01-后台管理网站需求文档.md`、`.harness/rules/03-工程硬性规范.md`

### 3.7 可测试性

- **问题**：当前需求分析还未把管理端用户域的最小验证矩阵写清楚，尤其缺少权限、状态迁移、幂等、契约一致性、联查视图的测试要求。这样会导致阶段6只能补碎片测试，无法形成完整门禁。
- **建议**：在需求基线或后续任务拆分中明确最小测试清单：后台权限校验、详情 DTO 契约、合法状态迁移、重复提交幂等、资金与收益只读/受控边界、消息发送结果追踪。
- **优先级**：P1
- **证据**：`01-需求分析文档.md`、`docs/api/openapi/openapi.yaml`

## 5. 回退与通过条件

### 回退结论

- 按工作流回退到阶段1，补齐需求基线中的以下内容后再发起第 2 轮需求评审：
  1. 8 个用户域各自的后台菜单/模块落位。
  2. 每域最小交付单元：列表、详情、联查、受控动作、禁止直改边界。
  3. admin 用户域 OpenAPI 契约补齐要求。
  4. 分层约束、RBAC/审计、幂等/状态机、测试矩阵作为强制门禁。

### 通过条件

满足以下条件后可进入阶段3任务拆分：

1. 需求分析文档已把 8 个域的交付边界写清。
2. 已明确后台只允许受控流程操作，不允许直改账务/状态结果。
3. 已将 OpenAPI、RBAC/审计、分层、幂等和测试要求纳入任务边界。
4. Reviewer 复核后无新的 P0 阻断项。
