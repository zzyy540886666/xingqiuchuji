## 2. 评审发现

| 维度 | 问题 | 建议 | 优先级 | 状态 |
| --- | --- | --- | --- | --- |
| 需求一致性 | 初始设计需避免将模糊的“活动信息”扩大为未在原需求定义的促销交易能力。 | 将一期活动限定为场景专题与运营配置，独立营销活动留作待确认扩展。 | P1 | 已解决，见需求文档 3.2/12 |
| 架构一致性 | 已有 admin 源码骨架含直接 Mapper 访问，若被视为目标模式会违反分层要求。 | 在架构文档声明骨架仅供盘点，后续写操作必须经 Service/Domain/DAO/Adapter。 | P1 | 已解决，见架构文档 4.1/4.3 |
| 契约一致性 | OpenAPI 当前只含健康检查占位，管理端路径不能被误称为已交付接口。 | 在文档索引、需求和架构中统一声明 admin 路径为目标设计，实施前补 OpenAPI。 | P0 | 已解决，见三份 admin 文档 |
| 安全性 | 后台将接触配置发布、审核、资金和导出等高权限资源。 | 明确后台独立鉴权、RBAC/数据范围、脱敏、二次确认、审计、生产 Secret 外置。 | P0 | 已解决，见需求文档 4/9 及架构文档 3.3/5.3/7.3 |
| 数据一致性 | 商品价格、资金、支付和结算被后台直接改写会破坏权威流水。 | 限制为领域服务受控变更、整数分、幂等、追加流水和版本化配置发布。 | P0 | 已解决，见需求文档 6.5/6.6/9 及架构文档 4/6 |
| 可观测性 | Docker 和外部适配若缺乏健康检查及容错说明，实施时无法可靠运维。 | 补充第三方超时/重试/降级、traceId、健康探针工具可用性及发布回滚要求。 | P1 | 已解决，见架构文档 4.2/8/9 |
| 可测试性 | 文档若不区分设计目标与已实现能力，后续验收条件不可判定。 | 使用里程碑与验收条件，并把 OpenAPI/RBAC/回滚演练定义为前置门禁。 | P1 | 已解决，见需求文档 10/11 及架构文档 10 |

## 3. 结论与后续门禁

- 阻断项：文档交付层面无未解决 P0/P1 发现。
- 评审结论：文档变更可进入仓库级 CI 验证；此结论不等同于管理端实施或部署已完成。
- 实施阻断项仍存在：活动扩展范围、角色数据权限、管理端 OpenAPI、指标口径及生产环境参数需人工确认后才可进入开发/部署。
- 若 CI 门禁失败：按结果回退到对应测试或实现阶段并记录，不声明最终通过。
