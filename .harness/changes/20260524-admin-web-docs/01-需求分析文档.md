# 后台管理网站需求与 Docker 架构文档 - 需求分析

## 1. 需求来源与目标

- 来源：用户于 2026-05-24 提出，要求结合 `docs/frontend/` 与 `docs/backend/`，为可操作小程序商品信息、活动信息、运营管理、数据分析等必要功能的后台管理网站设计需求文档与采用 Docker 的技术架构文档。
- 目标用户：平台管理员、运营人员、内容审核人员、财务/结算人员、客服或运维人员。
- 交付目标：在 `docs/` 下形成可供后续产品确认、API 定稿、前后端实施与容器化部署的后台站点文档基线。

## 3. 范围边界

### 3.1 本次范围

- 后台管理网站产品需求：角色、菜单、功能范围、核心流程、数据分析指标、验收要求。
- 技术架构方案：前后端边界、后台 API 规划、权限审计、安全观测、数据与缓存、Docker 容器化和发布回滚。
- 对既有文档与现有后台骨架之间的契约缺口做显式标记。

### 3.2 非目标范围

- 不在本次实现管理端页面、后台 API、数据库迁移或 Docker 配置文件。
- 不直接修改 `docs/api/openapi/openapi.yaml`；管理端路径与 Schema 需在需求确认后专项定稿。
- 不将尚未定义的优惠券、秒杀、营销规则引擎视为一期已确定能力。
- 不执行部署。

## 5. 契约、安全与质量约束

- 所有新增后台端点须归入 `/api/v1/admin/**` 并在实现前补入 OpenAPI 真源。
- 管理员登录与小程序用户会话分离；后台采用 RBAC 和资源/数据范围校验。
- 金额字段统一为整数分；支付、提现、分佣和状态处置不得在 UI 或临时脚本中直接改账。
- 配置、审核、上下架、角色、工单处置和导出操作须记录操作人、前后值、时间、traceId。
- 外部 COS/TMS/微信服务访问须设置超时、重试上限与降级路径。
- 后台页面必须具备 loading、error、empty 状态，不使用 emoji 作为功能图标。
- Docker 生产配置不得提交真实密码、密钥、证书；数据库与 Redis 数据卷需有备份和回滚说明。

## 7. 验证标准

- `docs/admin/` 下包含需求文档、Docker 技术架构文档和索引，且可追溯至现有 FE/BE/API 文档。
- 需求文档至少覆盖商品信息、活动/运营、数据分析及必要配套的权限、交易、审核、运维能力。
- 技术架构文档明确 Docker 拓扑、镜像/容器职责、配置与密钥、健康检查、持久化、发布及回滚路径。
- 文档不得将未进入 OpenAPI 的后台接口声明为现成契约，并明确金额、鉴权、幂等、审计和外部超时要求。
- 执行 `npm run harness:ci` 并记录程序化结果；若门禁受既有工作区问题阻塞，则如实记录而不虚构通过。

## 8. 风险与回退前提

- 风险：活动范围若需优惠核销、报名或秒杀，一期配置模型不能覆盖，必须回到需求分析并新增领域和契约设计。
- 风险：现有后台源码与最终文档不一致，实施前须以 OpenAPI 和已确认需求重新校核，不可直接照源码接 UI。
- 风险：后台涉及资金与管理员权限，未落实 RBAC、审计及隔离会形成高风险越权面。
- 回退前提：本次仅新增/调整文档和留痕，撤回时可单独撤销本变更目录及 `docs/admin/`/索引变更，不影响现行业务代码或数据。
