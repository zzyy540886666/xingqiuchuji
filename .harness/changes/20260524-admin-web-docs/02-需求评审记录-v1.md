## 2. 评审维度与意见

| 维度 | 问题 | 建议 | 优先级 | 责任人 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 需求一致性 | “活动信息”在已有 FE/BE 文档中没有独立业务定义，直接设计活动交易规则会越界。 | 将一期活动明确限定为场景专题、话题和版本化运营配置，并登记独立营销活动为待决议扩展。 | P1 | 文档设计 | 已纳入方案 |
| 架构一致性 | 源码存在后台骨架，但已有 Controller 直接访问 Mapper 的迹象，不能作为目标架构照搬。 | 技术架构坚持 Controller/Service/Domain/DAO/Adapter 分层，并将现有骨架治理列为实施任务。 | P1 | 后续实现 | 已登记 |
| 契约一致性 | `openapi.yaml` 尚未定义管理端 Schema/路径。 | 文档只提供待定 API 资源分组，明确实现前必须先补 OpenAPI 并生成客户端类型。 | P0 | 产品/后端 | 已设前置门禁 |
| 安全性 | 后台拥有配置发布、内容处置、资金查看等高权限能力。 | 建立后台独立认证、RBAC、数据范围、二次确认与审计日志要求；敏感导出脱敏。 | P0 | 架构/后端 | 已设硬约束 |
| 数据一致性 | 商品价格、支付、提现、分佣相关动作若被后台直接修改会破坏账务一致性。 | 一期资金后台以查询、审核状态流和受控任务为主；金额整数分；所有写操作走领域服务和幂等/流水。 | P0 | 产品/后端 | 已设硬约束 |
| 可观测性 | 管理动作及容器服务若无日志/指标会难以追责与定位。 | 强制 traceId、操作审计、登录/发布/审核指标、Docker 健康检查和告警基线。 | P1 | 架构/运维 | 已纳入方案 |
| 可测试性 | 仅有文字功能列表不足以支持后续验收。 | 每个模块给出关键验收场景，并提供 API 契约、权限、容器健康与回滚验证清单。 | P1 | 文档设计 | 已纳入方案 |

## 3. 评审结论

- 结论：在 P0 前置条件被文档明确为实施门禁的前提下，需求文档设计可继续产出。
- 阻断实施条件：管理端 OpenAPI 未定稿；后台角色权限与审计策略未确认；活动若超出配置型内容范围但未重新分析。
- 下一阶段：编写任务拆分清单及 `docs/admin/` 正式文档。
- 人工确认点：后续实施前，产品/负责人需确认活动一期边界、角色权限矩阵和管理端 API 范围。
