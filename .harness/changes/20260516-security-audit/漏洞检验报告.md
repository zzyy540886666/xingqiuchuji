### VULN-001 | P0 严重 | CVSS 9.8

**标题**: 支付回调验签 Mock 始终返回 true，导致支付状态可被伪造

**位置**: [WeChatPayClient.java:38-46](backend/src/main/java/com/xingqiu/server/payment/adapter/WeChatPayClient.java#L38-L46)

**类型**: 认证绕过 (CWE-287)

**描述**:
`WeChatPayClient.verifyNotify()` 方法当前为 Mock 实现，对任意输入始终返回 `true`。微信支付回调端点 `/api/v1/internal/pay/wechat/notify` 位于 SecurityConfig 的无认证白名单 `/api/v1/internal/**` 中。攻击者可直接向该端点发送伪造的回调数据，将任意订单状态变更为已支付 (PAID)。

**受影响资产**:
- `POST /api/v1/internal/pay/wechat/notify` — 无需认证
- 所有 `PaymentOrder` 记录 — 可被标记为 SUCCESS
- 所有 `Order` 记录 — 可被变更为 PAID 状态
- 关联的钱包余额 — 若支付成功触发佣金/入账逻辑，将导致资金损失

**复现步骤**:

```
步骤 1: 攻击者创建一个订单，获取 orderId（或直接猜测已知 orderId）
步骤 2: 构造 outTradeNo（格式: "XQ" + orderId + 毫秒时间戳，可预测范围）
步骤 3: 发送伪造的支付回调请求:

POST /api/v1/internal/pay/wechat/notify HTTP/1.1
Host: <target-host>:8080
Content-Type: application/json
Wechatpay-Signature: fake-signature

{
  "out_trade_no": "<构造的outTradeNo>",
  "transaction_id": "fake_txn_123456"
}

步骤 4: 服务端 verifyNotify() 返回 true → 验签通过
步骤 5: decryptNotify() 返回 Mock 数据 → 解析成功
步骤 6: handleCallback() 将 PaymentOrder 状态设为 SUCCESS
步骤 7: handleCallback() 将 Order 状态迁移为 PAID
```

**预期行为**:
支付回调必须经过微信 API v3 签名验证（使用 `WX_PAY_API_V3_KEY` 对回调体进行 HMAC-SHA256 验签，并验证证书序列号与微信平台证书一致），验签失败应拒绝处理。

**实际行为**:
`verifyNotify()` 无条件返回 `true`，任意伪造回调均被接受。

**修复建议**:
1. 替换 Mock 为真实的微信支付 API v3 回调验签逻辑
2. 在 `handleCallback` 中增加回调金额与支付单 `amountMinor` 一致性校验
3. 建议将回调端点路径移出 `/api/v1/internal/**` 白名单，单独配置为仅允许微信服务器 IP 访问
4. 增加 `Wechatpay-Timestamp` 和 `Wechatpay-Nonce` 头校验，防止重放攻击

### VULN-002 | P0 严重 | CVSS 9.4

**标题**: JWT 签名密钥存在硬编码默认值

**位置**: [application.yml:51](backend/src/main/resources/application.yml#L51)

**类型**: 硬编码凭证 (CWE-798)

**描述**:
JWT 签名密钥通过 `${JWT_SECRET:changeme-please-use-env-var-in-production}` 配置。若生产环境中 `JWT_SECRET` 环境变量未设置或加载失败，系统将回退到硬编码默认值。攻击者知晓此默认密钥后，可伪造任意用户（含管理员）的 JWT Token。

**受影响资产**:
- 整个认证体系 — 所有 JWT Token 可被伪造
- 所有需要认证的 API 端点
- 管理员端点 `/api/v1/admin/**`

**复现步骤**:

```
步骤 1: 攻击者获取默认 JWT 密钥: "changeme-please-use-env-var-in-production"
步骤 2: 使用该密钥签发 JWT:

  使用 JJWT 库或 jwt.io 在线工具:
  - Header: {"alg": "HS256"}
  - Payload: {"sub": "1", "role": "ADMIN", "iat": <当前时间>, "exp": <未来时间>}
  - Sign with: changeme-please-use-env-var-in-production

步骤 3: 使用伪造的 Token 访问任何 API:

GET /api/v1/admin/users HTTP/1.1
Authorization: Bearer <伪造的Token>

步骤 4: 服务端使用默认密钥验证 → 验证通过
步骤 5: 获得管理员权限
```

**预期行为**:
生产环境中 JWT 密钥必须通过环境变量注入，若缺失则应用启动失败。密钥应为高熵随机字符串（≥256 位）。

**实际行为**:
JWT 密钥存在硬编码默认值，环境变量缺失时静默降级使用。

**修复建议**:
1. 移除默认值，改为 `${JWT_SECRET}`（无默认值），缺失时启动即报错
2. 建议在 `JwtUtil` 构造函数中增加密钥长度校验（≥32 字节）
3. 生产环境使用 `Keys.secretKeyFor(SignatureAlgorithm.HS256)` 自动生成安全密钥
4. 考虑迁移到 RS256/ES256 非对称密钥，便于密钥轮换

### VULN-003 | P0 严重 | CVSS 6.5

**标题**: 订单详情接口未校验用户归属 (IDOR)

**位置**: [OrderController.java:41-44](backend/src/main/java/com/xingqiu/server/order/controller/OrderController.java#L41-L44)

**类型**: 不安全直接对象引用 (CWE-639)

**描述**:
`GET /api/v1/orders/{id}` 端点从 `SecurityContext` 提取当前用户 ID 用于 `createOrder` 和 `cancelOrder`，但 `getOrder` 方法完全未校验订单的 `userId` 是否匹配当前用户。任何认证用户可通过遍历订单 ID 查看他人订单详情，含金额、地址、租赁时间等敏感信息。

**复现步骤**:

```
步骤 1: 用户 A (userId=100) 正常登录，获取自己的 Token
步骤 2: 用户 A 创建订单，看到自己的 orderId=1
步骤 3: 用户 A 猜测或遍历 orderId:

GET /api/v1/orders/2 HTTP/1.1
Authorization: Bearer <用户A的Token>

步骤 4: 服务端直接返回 orderId=2 的订单详情（属于用户 B）
步骤 5: 用户 A 可遍历 id=3,4,5... 批量窃取所有用户订单数据
```

**对比 `cancelOrder`**:
`cancelOrder` 方法中有正确的归属校验：
```java
if (!order.getUserId().equals(userId)) {
    throw new BizException(ErrorCode.FORBIDDEN, "无权操作此订单");
}
```
但 `getOrder` 缺失了相同的校验。

**预期行为**:
`getOrder` 应校验 `order.getUserId()` 与当前认证用户 ID 一致，否则返回 403 或 404（避免 ID 存在性泄露）。

**实际行为**:
`getOrder` 无任何归属校验，直接返回任何 ID 对应的订单。

**修复建议**:
```java
@GetMapping("/{id}")
public ApiResponse<OrderResponse> getOrder(@PathVariable Long id) {
    Long userId = getCurrentUserId();
    OrderResponse response = orderService.getOrder(id, userId);  // 传入 userId 做归属校验
    return ApiResponse.ok(response);
}
```

**标题**: 支付创建接口未校验订单归属

**位置**: [PaymentController.java:18-22](backend/src/main/java/com/xingqiu/server/payment/controller/PaymentController.java#L18-L22)

public WeChatPayParams createPayment(Long userId, Long orderId) {

### VULN-005 | P0 严重 | CVSS 7.5

**标题**: 全站无速率限制机制

**影响范围**: 全部 Controller 端点

**类型**: 资源耗尽 (CWE-400)

**描述**:
项目中未引入任何速率限制组件（如 Bucket4j、Resilience4j、Guava RateLimiter）。所有端点均可被高频调用：
- 登录端点 `/api/v1/auth/wechat` 可被暴力枚举微信 code
- 支付/提现端点可被短时间内大量触发
- 数据库连接池仅 20 个连接 (Hikari max=20)，高并发下容易耗尽

**复现步骤**:

```
步骤 1: 攻击者编写脚本，对登录端点每秒发送 100+ 请求
步骤 2: 服务端逐一调用 WeChatMiniProgramClient（Mock 快速返回）
步骤 3: 每个请求消耗数据库连接和 Redis 连接
步骤 4: 连接池耗尽 → 正常用户请求被阻塞 → 拒绝服务

同样的攻击可针对任何端点:
  for i in {1..10000}; do
    curl -H "Authorization: Bearer <token>" http://host/api/v1/orders &
  done
```

**预期行为**:
关键端点（登录、支付、提现、发帖）应有基于 IP + 用户 ID 的速率限制。

**实际行为**:
无任何速率限制。

**修复建议**:
1. 引入 Spring 拦截器 + Redis 实现令牌桶/滑动窗口速率限制
2. 至少对以下端点实施限制：
   - `/api/v1/auth/**` — 每 IP 每分钟 10 次
   - `/api/v1/orders` (POST) — 每用户每分钟 30 次
   - `/api/v1/wallet/withdraw` — 每用户每分钟 3 次
   - `/api/v1/community/posts` (POST) — 每用户每分钟 5 次

### VULN-006 | P1 高危 | CVSS 6.5

**标题**: 提现接口幂等键自动生成致幂等保护失效

**位置**: [WalletController.java:48-54](backend/src/main/java/com/xingqiu/server/wallet/controller/WalletController.java#L48-L54)

**类型**: 业务逻辑缺陷 (CWE-841)

**描述**:
提现端点在 `WalletController.withdraw()` 中自动生成幂等键 `"WITHDRAW_" + userId + "_" + System.currentTimeMillis()`。即使客户端因网络超时重试相同请求，每次也会生成不同的幂等键，导致幂等保护机制完全失效。在任何超时重试场景下，可能创建重复提现记录。

**复现步骤**:

```
步骤 1: 用户钱包余额 10000 分，发起提现 5000 分
步骤 2: 请求在服务器端处理成功，但响应在网络层丢失（超时）
步骤 3: 客户端重试提现 5000 分
步骤 4: 第 1 次请求: idempotencyKey = "WITHDRAW_100_1715850000001" → 未命中缓存 → 创建提现
步骤 5: 第 2 次请求: idempotencyKey = "WITHDRAW_100_1715850015000" → 未命中缓存 → 再次创建提现
步骤 6: 用户被重复扣款 5000×2 = 10000 分
```

**注意**: `IdempotencyInterceptor` 已正确配置拦截 `/api/v1/wallet/withdraw` 路径。但 Controller 层又自行生成了新的 key 覆盖了客户端应提供的 key，使拦截器的 `SET NX` 去重失效。

**预期行为**:
幂等键应由客户端通过 `Idempotency-Key` Header 传入，服务端不应自行生成。

**实际行为**:
服务端每次自动生成新的幂等键，客户端重试无法去重。

**修复建议**:
1. 从 Controller 中移除自动生成幂等键的逻辑
2. 改为从请求 Header 读取 `Idempotency-Key`（`IdempotencyInterceptor` 已校验）
3. 若客户端未传入 `Idempotency-Key`，拒绝请求（对写操作幂等键应为必填）

### VULN-008 | P1 高危 | CVSS 8.6

**标题**: 四个核心外部依赖适配器均为 Mock 实现

**位置**:
- [WeChatPayClient.java](backend/src/main/java/com/xingqiu/server/payment/adapter/WeChatPayClient.java) — 支付下单、验签、解密全 Mock
- [WeChatTransferClient.java](backend/src/main/java/com/xingqiu/server/wallet/adapter/WeChatTransferClient.java) — 转账始终返回成功
- [WeChatMiniProgramClient.java](backend/src/main/java/com/xingqiu/server/auth/adapter/WeChatMiniProgramClient.java) — 返回伪造 openid
- [TmsModerationClient.java](backend/src/main/java/com/xingqiu/server/community/adapter/TmsModerationClient.java) — 85% 概率随机放行

**类型**: 安全控制缺失 (CWE-1240)

**描述**:
四个关键安全控制点目前全部为 Mock 实现。若其中任何一个以 Mock 形态部署到生产环境，将导致对应安全机制完全失效。当前没有 Profile 隔离机制区分 Mock 与真实实现。

**复现步骤**:

```
WeChatTransferClient Mock:
  任何提现请求 → transferToWallet() 始终返回 SUCCESS → 资金无损? 实际未调微信API
  风险: Mock 部署到生产 → 用户可以不断提现而不实际扣款

WeChatMiniProgramClient Mock:
  任意 code 输入 → 返回伪造 openid
  风险: 生产环境任何人都可登录（因为 code2session 不验证 code 有效性）

TmsModerationClient Mock:
  85% 概率随机放行内容
  风险: 违规内容（色情、暴力、政治敏感）15% 被拦截但 85% 放行
```

**修复建议**:
1. 使用 Spring `@Profile("mock")` 标记所有 Mock 实现
2. 创建真实实现并标记 `@Profile("!mock")`
3. 在 `application.yml` 中：`spring.profiles.active: dev`（开发用 mock），生产 Profile 不包含 mock
4. 添加启动时健康检查：验证与微信支付/腾讯云等外部服务的连通性

### VULN-009 | P1 高危 | CVSS 4.2

**标题**: PostService 使用 `.last()` 拼接原始 SQL

**位置**: [PostService.java:113](backend/src/main/java/com/xingqiu/server/community/service/PostService.java#L113)

**类型**: SQL 注入风险 (CWE-89)

**描述**:
```java
query.last("LIMIT " + Math.max(1, Math.min(limit, 50)));
```
MyBatis-Plus 的 `.last(String)` 方法将字符串直接追加到 SQL 语句末尾，不做参数化处理。当前情况下 `limit` 被 `Math.min/max` 约束在 [1, 50] 区间内，暂时安全。但此编码模式极易在后续维护中被修改为接受不受信任的字符串输入，导致 SQL 注入。

**复现步骤**:

```
当前代码下 limit 为 int 类型，被约束在 1-50，暂时无法注入。

但假设未来开发者做了如下修改（将 limit 改为 String 以支持更灵活的分页）:
  public List<PostResponse> getFeed(String cursor, String limit, Long topicId) {
      query.last("LIMIT " + limit);  // 直接拼接用户输入
  }

则攻击者可传入: limit = "1; DROP TABLE posts; --"
生成 SQL: SELECT ... LIMIT 1; DROP TABLE posts; --
```

**修复建议**:
使用 MyBatis-Plus 分页对象替代 `.last()`：
```java
Page<Post> page = new Page<>(1, Math.max(1, Math.min(limit, 50)));
Page<Post> result = postMapper.selectPage(page, query);
```

## 六、检验结论

后端代码整体架构规范（五层分层、Lambda 查询、状态机、统一异常处理），但**当前不具备生产就绪的安全性**。核心问题集中在两个方面：

1. **Mock 适配器无隔离** — 四个 Mock 实现中，支付验签 Mock (`VULN-001`) 与转账 Mock (`VULN-008`) 直接导致资金安全风险
2. **认证与授权缺口** — JWT 密钥默认值 (`VULN-002`)、订单 IDOR (`VULN-003/004`)、全站无速率限制 (`VULN-005`)

**建议**: 第一阶段 5 项 P0 修复全部完成并通过复审后，再进行任何生产环境部署。
