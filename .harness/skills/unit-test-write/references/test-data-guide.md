# 测试数据构造指南

测试数据必须贴近线上真实数据特征，不能用空壳数据糊弄。

## 基本原则

1. **脱敏但真实**：数据来源应为线上数据脱敏后的样本，或根据线上分布特征构造
2. **覆盖数据多样性**：考虑不同用户类型、不同订单状态、不同金额区间
3. **边界值优先**：金额 0、最小正整数、最大值；字符串空/null/超长；数组空/单元素/大量

## 分领域数据构造要点

### 用户相关

- 用户 ID：使用真实格式（如数字型或 UUID），不要用 "test"、"admin"
- 手机号：使用合法格式但明显是测试号的号码（如 1380000xxxx）
- 昵称：包含中英文、emoji、特殊字符的混合样例

### 订单/支付相关

- 金额：必须使用整数分，覆盖 1分、正常金额、大额、0元场景
- 订单状态：覆盖全部状态流转路径
- 时间：覆盖创建→支付→完成→退款的完整时间线
- 幂等键：同一键重复提交的场景

### 商品/内容相关

- 商品名称：包含特殊字符、超长名称、emoji
- 价格区间：覆盖低价、中价、高价
- 库存：覆盖充足、临界值（剩 1 件）、已售罄

### 通用边界

- null/空值：所有可选字段的 null 场景
- 超长字符串：超过数据库字段长度的输入
- 特殊字符：SQL 注入字符（`'`、`;`、`--`）、XSS 字符（`<script>`）
- 并发场景：同一资源的并发修改

## 数据来源

1. 优先从 `docs/api/openapi/openapi.yaml` 中提取字段定义和枚举值
2. 从 `docs/backend/BE-XX.md` 中了解业务规则和数据分布
3. 测试数据脱敏后写入测试类的 fixtures 或 @BeforeEach 方法

## 反面案例

```
// 错误：空壳数据，不代表真实场景
User user = new User("test", "123", 0);

// 正确：贴近真实数据特征
User user = new User("张三", "13800138000", 9900); // 99.00元
```
