# 评审检查清单

评审时按维度逐项核对，每项确认后打勾。未覆盖的维度视为评审不合格。

## 1. 需求一致性

- [ ] 功能是否覆盖需求分析文档（01-需求分析文档.md）中的全部目标范围
- [ ] 是否有需求外的额外功能（范围膨胀）
- [ ] 非目标范围是否未被改动
- [ ] 需求来源（产品文档/口述/工单）是否在代码或注释中有据可查

## 2. 架构一致性

- [ ] Controller 是否只做参数接收与响应封装（不含业务逻辑）
- [ ] Service 是否只做用例编排与事务管理（不含持久化细节）
- [ ] Domain 是否只做业务规则与状态机（不含框架注解）
- [ ] DAO 是否只做参数化 SQL/MyBatis 映射（无拼接）
- [ ] Adapter 是否只做外部依赖调用（有超时/重试/降级）
- [ ] 无越层调用：Controller→DAO、Domain→SDK 均不存在

## 3. 契约一致性

- [ ] 接口路径与 HTTP 方法与 openapi.yaml 一致
- [ ] 请求/响应字段名与 openapi.yaml 一致
- [ ] 枚举值与 openapi.yaml 一致（无新增未注册枚举）
- [ ] 错误码与 docs/api/00-接口通则.md 中的命名规则一致
- [ ] 分页参数语义与通则一致

## 4. 安全性

- [ ] 所有外部输入经过类型/范围/长度/枚举校验
- [ ] 无字符串拼接 SQL（必须参数化）
- [ ] 用户输入展示前已消毒（防 XSS）
- [ ] 金额字段使用整数分，无 float/double
- [ ] 支付/回调/关单流程已实现幂等
- [ ] 敏感配置（密钥、密码）不在代码中硬编码
- [ ] 接口鉴权注解齐全（@RequireAuth 或等效）

## 5. 数据一致性

- [ ] 事务边界清晰（哪些操作在同一事务内）
- [ ] 幂等键在并发场景下不会重复执行
- [ ] 缓存与 DB 的更新顺序有明确策略（Cache-Aside/Write-Through）
- [ ] 分布式场景下有唯一键/乐观锁防重复

## 6. 可观测性

- [ ] 关键业务操作有日志记录（INFO 级别以上）
- [ ] 日志包含 traceId（可串联全链路）
- [ ] 外部调用失败有降级路径和告警
- [ ] 异常未被吞掉（无空 catch 或仅 e.printStackTrace）

## 7. 可测试性

- [ ] 核心业务逻辑可被单元测试覆盖（无硬编码外部依赖）
- [ ] 接口可被集成测试调用（有明确的入参/出参）
- [ ] 测试数据可构造（有 Factory 或 Builder 或测试 fixtures）
